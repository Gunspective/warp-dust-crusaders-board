# Warp Dust Crusaders coach board: contract

What the board must do, and how it does it today ("as built"). The forecast maths is written out in full in `METHODS.md`; the player-history snapshot and the weights are in `HISTORY.md`; setup and operation are in `../README.md` and `RUNBOOK.md`.

Owner, 2026-10-16 (verbatim where quoted): "Excels sheets are outdated. I just need during pairings a live link to their list off of BCP. There elo needs to be next to the list. Faction and dispo as well. From there on the tablet, the coach needs to have a grid where predictions are shown on a cover page. If clicked its a grid from 0-20 for the player to click on once the coach comes up and it puts the score in. Come up with how many points you need to win, draw, and loss and show that prediction as well." Then: "Make it fit on a tablet." Then: "We should already be only able to pair into 3-4 other teams." Then: "Run the elo check all of these guys cant be only 1400."

The board first shipped on 2026-10-16 as a page of another site and was moved to this standalone project on 2026-10-19. The prototype it was ported from is `warp-dust-crusaders-site/source/teo8-2026-10/board-template.html`; its look, copy and interactions are the spec.

## C1. Page and reach
- `GET /` (and any other page path, through the single-page fallback) serves the board: a full-screen tool for the Warp Dust Crusaders (a Warhammer 40K team), with no other site chrome. It carries `<meta name="robots" content="noindex,nofollow">` and every response from the Worker carries `X-Robots-Tag: noindex, nofollow`. It is private by obscurity: anyone with the link can read it, nothing links to it, and only the coach PIN can change it.
- Works at 1280x800 and 1024x768 landscape with no scrolling (Fire HD 10 and iPad landscape tablets), and at 400px wide as a scrolling column.
- (as built) Fonts load from `https://fonts.bunny.net` (Saira + Barlow, same families and weights as the prototype) through the stylesheet link in `index.html`; the Worker's Content-Security-Policy allows fonts.bunny.net and nothing else outside this origin (`src/worker/headers.ts`).
- (as built) `src/app.tsx` fetches the first board from `GET /api/board` (with a "Loading the board" line, and "Could not reach the server" plus Try again on failure), then renders `WdcBoard`, which polls on its own.

- (as built) Caching: content-hashed files under `/assets/` are served `public, max-age=31536000, immutable`; the page and any HTML fallback revalidate (`max-age=0, must-revalidate`); `/api/*` is `no-store`.
- (as built) On tablets a player name on a table card is one line with an ellipsis (full name in `title`), so a two-line name can never push the card's controls past its edge at 1024x768; phones keep the full wrapping name.

## C2. Data: BCP is the source for rosters, pairings and posted scores
- BCP's public API answers without a login with the header `client-id: web-app` (proven 2026-10-16):
  `https://newprod-api.bestcoastpairings.com/v1/events/{eventId}` (event),
  `/v1/events/{eventId}/teamPlayers?placings=true` (team standings),
  `/v1/events/{eventId}/pairings?eventId={eventId}&pairingType=TeamPairing&round={n}` (team matches),
  `/v1/events/{eventId}/pairings?eventId={eventId}&pairingType=Pairing&round={n}` (the eight player games of each team match).
- (as built) Player rows carry `subFaction` as the disposition, `listId`, and `player{1,2}Game.points` as the 0..20 score; an unpaired round answers 200 with `{active: []}`, which ends the round loop. A player's own `team` label is unreliable (53 of 128 seats in the fixtures), so each seat is attributed to a team through its `teamPairingId` and the label is only a fallback. A table score counts as posted by BCP only when the game is done or the points are above 0 (`src/lib/wdc/bcp.server.ts`).
- Every BCP call runs in the Worker, never from the browser, and is cached for 60 seconds so a tablet polling every 30 s and a dozen phones do not hammer BCP. A BCP failure never blanks the page: the last good state renders with a "BCP unreachable since hh:mm" line.
- (as built) The 60 s cache is per URL in Worker isolate memory; failures are never cached. The last good snapshot is remembered in KV key `wdc.snapshot.{eventId}` and served with `stale: true` when BCP fails; with no snapshot at all the page renders an empty board rather than an error. KV writes are metered, so the snapshot is rewritten only when BCP's content changed, or every 15 minutes while it is unchanged (`WDC_SNAPSHOT_REFRESH_MS`); the hh:mm is therefore within 15 minutes of the true last good read, in the viewing device's clock (`src/lib/wdc/state.server.ts`, `src/components/wdc/model.ts`). A snapshot write KV refuses is skipped, never waited on.
- Event id lives in KV key `wdc.event` (default `JkPs5aELBHPh`, TEO-8 "All in.", Hopkinsville KY, 2026-10-16 to 18, 17 teams, 5 rounds). Our team name: KV key `wdc.team` (default `Warp Dust Crusaders`), matched to BCP's spelling case- and punctuation-insensitively.

- (as built) A save never waits on BCP when a snapshot is stored: after the PIN check it writes the coach document first, then answers from the stored snapshot of any age (marked stale only when older than `WDC_SNAPSHOT_STALE_MS`, about 17 minutes); BCP is called only when nothing is stored. The 30 s poll is what refreshes from BCP.

## C3. State the coach owns (overrides on top of BCP)
- Stored as one JSON document in KV key `wdc.state.{eventId}`: `{ rounds: { [n]: { opp?: string, players: { [normalizedUsName]: { score: number|null, nudge: number } } } }, pairing: { opp: string, locks: [{us, them}] }, eloOverrides: { [playerName]: number }, weights?: { faction, form, history } }`.
- (as built) Coach entries are keyed by OUR player, never by table number: the key is `normalizeName(us)` (`src/lib/wdc/elo.ts`, applied as `coachPlayerKey` in `src/lib/wdc/keys.ts`). Table numbers are not stable (a lock-built round is numbered by lock order and BCP posts the same games under other numbers), a player is. `mergeBoard` gives every table of every round, BCP-posted or lock-built, the entry `players[normalizeName(table.us)]` of that round, so an entry follows its player onto whatever table BCP seats them at. A save stores the document exactly as the page sent it.
- (as built) `opp` is the opponent the page showed for the round when it wrote the entries (`withTable`, `src/components/wdc/model.ts`). When a round's stored `opp` is set and the round's actual opponent differs (compared through `teamKey`, the same rule as `bcpTeamKey`, pinned equal by a test), none of that round's entries show, but they stay stored and show again if BCP corrects the pairing. An entry whose player BCP has not seated shows nowhere and stays stored until BCP seats that player. The first write against an opponent other than the stored `opp` starts that round afresh. A round carrying the retired table-keyed `tables` field, or a player key not already in `normalizeName` form, is refused.
- A posted BCP result wins over a coach-entered score once BCP has it; the coach's score shows until then. Nudges are coach-only and shift the forecast by whole points.
- Writes are gated by a PIN. The stored form is the hex SHA-256 of the PIN, never the PIN: KV key `wdc.pin.sha256` if present, otherwise the Worker secret `WDC_PIN_SHA256`. With neither, saves answer "Coach PIN not set". The secret `WDC_PIN_OFF` set to exactly `1` switches the PIN off: saves need no PIN, are not throttled, and the board reports `pinSet: false`. The browser keeps the PIN in localStorage (`wdc.pin`) after the first successful save with a typed PIN and sends it on every write.
- (as built) The save is `POST /api/save` with the JSON body `{coach, pin}` (`saveWdcCoachState({data: {coach, pin}})` in `src/lib/api/wdc.functions.ts`). The reply is always a JSON envelope: `{ok: true, state}` (200), or `{ok: false, reason, message}` with `reason` one of `"pin-unset"` (403, "Coach PIN not set"), `"pin"` (403, "Wrong PIN" or "Enter the coach PIN"), `"invalid"` (400: not JSON, not an object with a `coach` object and a string `pin`, a document out of shape, a PIN over 64 characters; 413 "Coach document too large" over 64 KB as UTF-8 JSON; 415 when the body is not `application/json`) or `"unavailable"` (429 "Too many tries"; 503 when KV is missing or fails). The page opens the inline PIN form on `"pin"` and `"pin-unset"` and toasts the message otherwise, whatever the HTTP status. The typed PIN is trimmed before it is compared, and a PIN whose first letter a phone keyboard capitalised also matches (one attempt). The stored hash is trimmed and lower-cased before the compare, so a hash written with a trailing newline still works.
- (as built) Brute-force throttle: 10 wrong PINs inside one fixed 10-minute window, opened by the first wrong PIN, lock every save request, correct PIN included, with `reason "unavailable"` and message "Too many tries". The counter is JSON `{count, windowStart}` in KV key `wdc.pin.fails2`; locked requests write nothing; a blank PIN is never counted. Check order is parse, storage, throttle, PIN.
- (as built) The throttle is BEST EFFORT. Workers KV has no atomic increment, so the counter is a read, then a write: requests that race (a parallel burst) all read the same count and each get their PIN compared, and KV's eventual consistency between Cloudflare locations (up to about 60 s) lets guesses through different locations see lower counts. Sequential guesses from one place are throttled as designed. The PIN is compared before a miss is counted, so the coach's own saves never write the counter (a correct PIN writes it only to clear live misses). A miss whose counter write KV still refuses after the retries answers "Too many tries" (fail closed). For a strict limit add a Cloudflare rate-limiting rule on `POST /api/save` or move the counter to a Durable Object (README.md, "PIN throttle"). The owner lifts a lockout early by deleting `wdc.pin.fails2` with wrangler.
- (as built) KV refuses a second write to one key inside about a second. The board's save queue can send two saves back to back, so coach-document and counter writes retry up to 3 times, 1.1 s apart (`WDC_KV_WRITE_TRIES`, `WDC_KV_RETRY_MS`), before they count as a failure.
- (as built) The server validates the whole document before storing it: at most 12 rounds of at most 16 player entries each, player keys in `normalizeName` form, `opp` a string, score null or integer 0..20, nudge integer -20..20, at most 8 locks, at most 200 `eloOverrides` with values 100..3000, names at most 120 characters, weights each 0..2 on a 0.25 grid. The count caps are checked first, so an oversized document is refused without walking it; a save replaces the stored document (`parseCoachState`).
- Reads (`GET /api/board`) need nothing: anyone with the link sees the board.

## C4. Forecast and the win line
- Per table: `expected = 1 / (1 + 10^((themElo - usElo)/290))` (owner 2026-10-17: 400 kept predictions at 7-13; 290 spreads a 100-point edge to 14-6, 200 to 17-3); forecast points for us = `round(20 * expected)` clamped to 0..20, plus the coach nudge (clamped again to 0..20). Predictions cover the full 0-20 range; the nudge runs -20..20.
- (as built) Faction edge: every forecast (board cards, strip totals, score pad outline, pairing grid) is `forecastPoints(usElo, themElo, nudge, edge)` with `p = 1 / (1 + 10^((themElo - usElo)/290) * e^(-edge))`; edge 0 gives exactly the Elo-only number (`src/lib/wdc/types.ts`). The faction edge is our faction's win rate against theirs (draws count half), shrunk toward 50% with K = 20 pseudo-games, clamped to 0.05..0.95, as log-odds; an unknown faction, a mirror or no row is 0 (`src/lib/wdc/matchups.ts`). BCP faction names are folded and aliased onto Stat Check's. The data is `src/lib/wdc/matchup-snapshot.json`, built by `scripts/statcheck-matchups.mjs` from Stat Check's public Matchup Matrix dashboard. A pairing-grid cell the faction edge moved by 2 or more points shows a small "F".
- (as built) Player history and weights: see `HISTORY.md`. `pairForecast` (`src/components/wdc/model.ts`) is the single source for every forecast and adds `wFaction * factionEdge + wForm * formEdge + wHistory * historyEdge` to the Elo log-odds before `round(20p)`, the clamp and the nudge. The snapshot `src/lib/wdc/player-history-snapshot.json` is loaded through `import.meta.glob` in `src/components/wdc/history-data.ts`, so a missing file builds and runs with no history. The coach changes weights from the "Weights" button in the header; a small "H" marks a pairing cell the history terms moved by 2 or more.
- Team match: 8 games, 20 points each, 160 total. 81+ wins, exactly 80 draws, 79 or less loses. The strip shows predicted total, locked points, projected total (locked + forecast of unplayed tables), and "to win: N more from M tables (x.x per game)" / "to draw: N" / "Match won" / "Out of reach" / "Draw is the ceiling".

## C5. Elo
- Source order per player: `eloOverrides` (coach), then the Stat Check table (C5a), then 1400 marked unknown (grey, not bold). Implemented in `mergeBoard`. The tablet has no screen for entering `eloOverrides`; they are a field of the stored coach document (RUNBOOK.md, known limits).
- C5a. Stat Check publishes its Elo table on https://www.stat-check.com/elo as an embedded OneDrive workbook. `scripts/statcheck-elo.mjs` drives the embed with Playwright to get the workbook's pre-authorized download, reads Sheet1 (Name, Elo) and writes `src/lib/wdc/elo-snapshot.json` as `{ generatedAt, source, players: { [normalized roster name]: elo }, misses: [...] }`, restricted to the event's roster, with every miss named with its reason. TEO-8: 103 of 136 matched; the 33 misses are 3 display handles (never guessed), 8 names the table lists twice with different Elo, and 22 not in the table or without a single prefix candidate.
- Name matching: exact after lowercasing, accent folding and collapsing whitespace; then a fallback that needs the SAME last name AND one first name a prefix of the other with at least 3 letters (sam/samuel yes; vinny/vinicius, cj/christian, aaron/ash no), only when exactly one table row fits; a fallback hit that is another roster player's own name is dropped; BCP display handles like "Butters s", "A. Lee", "dylan 40k" are never guessed (`isFullName`, `src/lib/wdc/elo.ts`).

## C6. Pairing view
- "Pairing" tab: choose the opponent. The picker lists only the plausible next opponents: teams within one match result (2 match points) of us in the live BCP standings, excluding teams we already played and ourselves, sorted by standing; "show all" reveals the rest.
- 8x8 grid, our players as rows, theirs as columns; each cell is the forecast for that pair (green at 12+, red at 8 or less), with faction, disposition, Elo and a List link on every header. Tapping a cell locks that pairing (table number = lock order); tapping again unlocks; locked rows and columns dim. Each of our players' best remaining matchup is outlined. "Set tables for round N" turns the eight locks into that round's tables and jumps to the board.
- (as built) A lock-built round is exposed only when exactly 8 locks exist, the round is the next one in range, BCP has not published it, and the opponent is not already played; its table number is the lock order and `fromBcp` is false. When BCP posts the round, each BCP table shows the entry of the player BCP seated there (C3); no save, stale or not, moves an entry to another player (regression tests (a) to (f) in `src/lib/wdc/state.test.ts`, end to end through `saveCoach` and `loadBoard` on the real round 2 fixtures). A tapped pairing cell's forecast and history record also show as text in a detail line under the grid.

## C7. Score pad
- Tapping a table card opens a full-screen pad: 0..20 as 21 large buttons (7 per row), the forecast outlined, one tap saves our points (theirs = 20 minus ours) and closes. "Clear score" is on the pad when the coach has a saved score for that table. Saving shows a toast; a PIN refusal shows the PIN entry inline and retries after the PIN is entered.
- (as built) One save is in flight at a time; taps during it coalesce into the newest whole document; a poll that began before a save and lands after it is discarded (epoch guard); a refused save rolls the screen back to the last confirmed board. The screen stays awake while the board is open on tablets that allow the Screen Wake Lock.
